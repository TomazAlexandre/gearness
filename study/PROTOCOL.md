# Study protocol: does a harness make coding agents fail less?

**Status:** draft v0.1. Freeze it (commit, no further edits) before the first measured run. `run.mjs` records the
protocol's hash and last commit in every manifest and refuses to measure while the file has uncommitted changes.
Any change after freezing is a deviation and goes in `DEVIATIONS.md` next to the results, with the reason.

Why this file exists: the question "does it work?" is easy to answer favourably by choosing tasks, conditions or
metrics after seeing the numbers. Writing the rules first removes that option, for us and for readers.

## 1. Question and hypotheses

> Given the same agent, model, code and tasks, does the harness around the agent change how often the work is correct?

| Id | Hypothesis | Type |
|---|---|---|
| H1 | A full gearness harness has a higher pass rate than a minimal harness (`full` > `minimal`). | **primary** |
| H2 | A full gearness harness has a higher pass rate than an auto-generated one (`full` > `bloated`). | **primary** |
| H3 | An auto-generated entry file helps or hurts relative to nothing (`bloated` vs `none`). No direction assumed. | exploratory |
| H4 | The harness changes cost per run (tokens, time). No direction assumed. | exploratory |
| H5 | The `gearness doctor` score is positively rank-correlated with pass rate across study × condition points. | exploratory |

H1 is **not supported** if the 95% interval of the difference includes zero or lies below it. We publish the result
in every case. A null or negative H1 is a finding about harness engineering, and about gearness, not a failure to hide.

## 2. Conditions

All conditions get the same code, the same tasks, the same agent and model, and the same flags. They differ only in
the files that instruct the agent. Before any condition is built, every agent instruction file, MCP config and gearness
harness (with the context docs its `harness.yaml` declares) is removed from the repository, so no condition inherits
a harness by accident.

| Condition | What the agent finds in the repository |
|---|---|
| `none` | Nothing. No instruction file of any kind. |
| `minimal` | One short entry file: how to run the tests and nothing else. |
| `bloated` | The entry file produced once by the agent's own init command (for Claude Code, `/init`), committed unedited. This is the comparison the field will ask for: unstructured context may hurt, and `full` has to beat it. |
| `full` | A harness built with gearness: `init`, the TODO markers filled with real knowledge, declared boundaries, adapters synced, hook and MCP configured. |

**How `full` and `bloated` are built (anti-bias rules).**
1. The person writing `full` has **not seen** the tasks, hidden checks or reference patches of that repository. They
   see the repository only.
2. Writing `full` is time-boxed to **60 minutes** per repository. Overlays are committed under `conditions/` and
   published whole, so readers can judge whether the harness is realistic or tailored.
3. `bloated` is generated by running the init command once. No retries, no edits.
4. Overlays are frozen before the first measured run.

## 3. Targets and tasks

**Two studies, reported separately and never pooled into one claim.**

- **Study A, controlled.** A small purpose-built repository whose conventions an agent cannot guess from code alone
  (layering, money in cents, injected clock, generated code). Shows the *mechanism*: when a harness can matter and by
  how much. Because we designed the tasks, it is a demonstration, not evidence of general benefit, and is labelled so.
- **Study B, real repositories.** Two or more open-source repositories with a permissive licence, in different stacks.
  Tasks come from real merged pull requests, not from us.

**Task selection (Study B), decided before any measured run and blind to condition outcomes:**
- Source: merged PRs with an automated test that fails before the change and passes after it.
- The prompt is written from the issue or PR description and contains **no solution hints**.
- The hidden check is the PR's test, never visible to the agent.
- Prefer PRs merged **after** the agent model's training cutoff, to limit memorization. State each PR's date.
- Every task must pass `validate.mjs`: its check **fails on the untouched code and passes with the reference patch**.
  A check that cannot do both measures nothing.
- Target: 5 tasks per repository, at least 3 repositories before any general claim.
- **Tasks are never added, dropped or edited after seeing results.** The only exception is a task that fails
  validation, which is reported as a deviation.

**Pilot.** A pilot (a few tasks, few runs) is used only to find infrastructure problems and estimate cost. Pilot results
are never reported as findings and never pooled with the study. A study that is re-run gets a **new study id**.

## 3b. Isolation of the experiment

- The repository given to the agent is the pinned commit **without git history**, so the real solution of a later commit
  is unreachable with `git log`.
- Task files and hidden checks live outside the agent's worktree. They are never tracked and never in its working directory.
- The agent runs in a clean environment: no user-level instruction files (for Claude Code, no `~/.claude/CLAUDE.md`), a
  fixed model, a recorded agent version. Prefer a container or a fresh user.
- **Known gap:** an agent with shell access could in principle read outside its worktree. The kit does not prevent that.
  Run in a container with only the worktree mounted when possible, and spot-check transcripts of passing runs.

## 4. Procedure

1. Pin the code commit. Build one trial repository per condition (single commit, stripped, overlay applied).
2. Run `validate.mjs --strict`. Do not continue if any task is invalid. `run.mjs` enforces this: it refuses to measure
   unless a validation recorded for this exact commit, task files, hidden checks and reference patches exists, and the
   manifest records which validation the run relied on.
3. Run `rounds`: for each round, each condition once, in a shuffled order (seeded). Within a round every task runs once,
   in its own git worktree. Interleaving makes model or API drift over the hours a study takes hit all conditions alike.
4. Runs per task and condition: **at least 5**.
5. Per-run timeout per task (default 15 minutes). Same value for every condition.

## 5. Metrics

**Pass** (as `gearness eval` defines it): the hidden check exits 0, **and** the agent did not change any forbidden file,
**and** the agent did not time out.

| Metric | Role |
|---|---|
| Macro pass rate: the mean over tasks of each task's pass rate (valid runs only) | **primary** |
| Cost per run (USD, from the agent's own report), turns, tokens, wall time | secondary |
| Forbidden-file violations (touched files the task said must stay untouched) | secondary |
| Invalid-run rate | quality control |
| `gearness doctor` score of each condition | for H5 |

**Invalid run:** setup failed, or the agent exited non-zero without changing any file (a crash, an authentication or
rate-limit error). Invalid runs say nothing about the harness. They are excluded from the primary analysis, **counted and
reported**, and shown as failures in a sensitivity column. If a condition has more than 10% invalid runs, that condition
is reported as unreliable and the fix goes into a **new study id**, not a patched old one.

## 6. Analysis

- Unit of analysis is the **task**. Runs of one task are not independent, so a run-level test would overstate certainty.
- Interval for a pass rate and for a difference: **cluster bootstrap**, 10,000 resamples, 95% percentile interval, fixed
  seed. Tasks are resampled first, runs within them second; differences are paired by task.
- The run-level rate with a Wilson interval is shown for reference, never as the headline.
- **Decision rule:** a difference is reported as an effect only if its 95% interval excludes zero. Otherwise it is
  *inconclusive*, and the report says so in those words.
- **Multiplicity:** two pre-registered comparisons (H1, H2), both always reported. Everything else is labelled
  *exploratory* in the table and must not be quoted as a finding.
- H5: Spearman rank correlation over (study, condition) points, computed only with 6 or more points.
- With few tasks the intervals are wide. That is the honest answer, not a defect to fix by adding runs of the same tasks.

## 7. What we publish

- Raw per-run results (`results/raw/*.json`), the metrics file, the manifest (versions, seed, commits, hashes, agent
  version) and the generated report. Anyone can regenerate the report from the raw files with one command.
- All overlays, tasks (including prompts), reference patches and the checks, once the study is complete.
- A `DEVIATIONS.md` listing every departure from this protocol. If there are none, it says so.
- Negative and null results. If a component of the harness did not help, we say so.

## 8. Threats to validity

| Threat | Mitigation | Still open |
|---|---|---|
| We author the harness we are testing | Blind, time-boxed construction; overlays published | Author bias cannot be fully removed; replication by others is the real fix |
| Few tasks, wide intervals | Task-level bootstrap; no claims beyond the interval | General claims need more repositories |
| Model has memorized popular repositories | Recent PRs, less famous repositories | Cannot be ruled out |
| One agent (Claude Code) | Agent is configurable | Other agents not yet studied |
| Task authors favour conventions harnesses capture | Study A is labelled a demonstration; Study B tasks come from real PRs | Selection of PRs is still ours |
| Checks can be passed by the wrong means | Forbidden-file list; check must fail on base code | Hidden tests may under-specify behaviour |
| Model and API change over time | Version recorded; conditions interleaved | A re-run later may differ |
| Agent can read outside its worktree | Hidden files outside the repository; container advised | Not enforced by the kit |
| The harness score may not measure effectiveness | H5 tests this directly; reported either way | See §9 |

## 9. Known limitations of the score

**Fixed before freezing.** In gearness 0.2.0 a project with a bare `harness.yaml` and no entry file scored about 82/100
(grade B). Rules that examine the entry file's content pass vacuously when there is no file; `context/placeholders` alone
is worth 30 of 162 points. Without the entry file the score is now capped at 39 (grade F), and `doctor` states the cap
and what the score would have been. Each manifest records the exact gearness commit, so scores are traceable to the
formula that produced them.

**Narrowed after 0.3.0.** The rule `context/entry-substance` (12 of 174 points) checks five signals in the entry file:
enough real content, at least two sections, a runnable command, a pointer to an existing file or folder, and at least one
explicit rule. A three-line `AGENTS.md` went from about 91 (grade A) to 81 (grade B).

**Still open.** The separation is modest: `context/placeholders` (30 of 174 points) still awards full marks to any file
without scaffold TODO markers, however thin. H5 therefore tests a score that separates *no harness* from *some harness*
well and *thin* from *substantive* only partly. H5 stays exploratory and is published either way. Scores must not be
re-tuned after seeing outcomes.

## 10. Later studies (out of scope here)

Ablations by component (documentation alone, lint rules alone, hook alone, MCP alone), other agents, and a longitudinal
study of the ratchet over weeks of real use.
